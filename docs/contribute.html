01

Embedded C++

Firmware

PlatformIO, the Arduino framework, one ESP32-C3 SuperMini. Clone, ./flash.sh, and you have a serial prompt in under a minute.

The architecture is deliberately dull: one class per peripheral, a single configuration header, and a main loop that never blocks. The interesting part is the head interpolation — it holds a target angle and walks the current angle toward it on a timer, which is the whole reason the movement reads as a character rather than a machine.

Adding a command touches four places: the parser, the on-device help text, the controller app's cheat sheet, and the protocol documentation. Miss one and someone spends an evening confused.

02

Web

Software

Two things: the controller app and this website. Both are plain HTML, CSS and JavaScript, served statically, with no build step and no framework. That is a constraint worth defending — it means the app can be served from a phone, a laptop, or a memory stick.

The site is hosted from a subpath on GitHub Pages, so every asset and link path must be relative. An absolute path beginning with a slash is the single most common way a Pages site ships broken.

Good first tasks

  • A keyboard driving mode for the controller — arrow keys to A/B speeds
  • A connection-state indicator that distinguishes “no Bluetooth” from “not connected”
  • A command log, so a builder can see exactly what was sent
  • Reduced-motion and dark-mode passes on both surfaces
03

CAD and printing

Mechanics

The CAD model is the master; meshes are derived from it. Never edit a mesh directly — a corrected STL is a dead end, because the next export overwrites it.

Part numbering is fixed at 01–08 and is used by the drawings, the tables and eventually the assembly steps. If you add a part, it takes the next number; nothing gets renumbered.

Keep individual files under about fifty megabytes. An oversized mesh is almost always over-tessellated rather than genuinely complex — 01_body.stl was once a 454 MB export of what is essentially a printed box.

Most valuable thing you could do

Assemble one and draw the steps

The seventeen steps are written; not one of them has a picture. Build a Marvin, photograph each stage as you go, and the sequence becomes something a stranger can follow without reading. A face-plate mesh, validated print settings and the assembled dimensions are worth almost as much.

04

PCB design

Electronics

This is the largest open invitation in the project, and it is now a well-posed one. Two boards have been specified down to part numbers, I²C addresses and a six-wire harness — and neither has been drawn. The specification is in Electronics.

What exists besides that is hand-soldered wiring that works, a pin map, and a known brownout problem: servos and motors drawing together sag the rail enough to reset the microcontroller, which shows up as a Bluetooth disconnect mid-drive. Giving the logic rail its own regulator is half of what the main board is for.

Wanted, in order

  1. A KiCad schematic for each board, drawn against the specification
  2. A measured current budget — the rails were chosen, not verified
  3. A layout for each board that fits inside part 01 and part 05
  4. Firmware for the CH32V003, and the I²C register map the ESP32 will talk to
  5. One fabricated set, and an honest account of what was wrong with it

Conventions that actually matter

Seven rules. Each one exists because breaking it caused a problem.

  1. 01One configuration header. Every pin and tuning constant lives in config.h. Never hard-code a pin inside a driver — this is what makes moving to a different microcontroller a config change rather than a rewrite.
  2. 02The main loop never blocks. Every periodic behaviour is a timer-based state machine. No delay() — it would stall Bluetooth and the console.
  3. 03One class per peripheral, in its own header and source pair.
  4. 04A new command touches four places. Parser, on-device help text, the app's cheat sheet, and the protocol documentation.
  5. 05No build step in the controller app. No framework either. It is deliberate, so the app can be served from anywhere. Keep it that way.
  6. 06CAD is the master; meshes are derived. Never edit a mesh directly.
  7. 07Nothing over about 50 MB in the repository. An oversized mesh is usually over-tessellated, not complex.
