Reference

The dense material, set as reference rather than narrative. Nothing here is explained twice; the explanations are in Build, Electronics and Drive.

Command protocol

Line-based text, identical over USB serial and Bluetooth. Case-insensitive, one command per line, values clamped rather than rejected.

CommandRangeMeaning
R<angle>0–180Head rotation (pan), centre 90 — e.g. R90
T<angle>30–85Head tilt, centre 57 — e.g. T45
M<speed>−255–255Both motors — e.g. M128
A<speed>−255–255Motor A only (one track)
B<speed>−255–255Motor B only (the other track)
S—Stop
D—Toggle demo mode

Any movement command cancels demo mode automatically. Tilt is limited to 30°–85° to protect the neck from its mechanical stops; pan is the full 0°–180°.

Bluetooth service

The Nordic UART Service — the de-facto standard for serial over Bluetooth. Any generic BLE terminal can drive the robot, not only the project's own app. Advertised name: Marvin. One client at a time.

Pin map

The hand-soldered build, on an ESP32-C3 SuperMini — this is what the firmware ships with. All of it lives in config.h; nothing is hard-coded in a driver. The ESP32-S3 allocation for the Marvin PCBs is in Electronics.

FunctionGPIO
Servo — tilt1
Servo — pan4
Motor A — IN1 / IN25 / 6
Motor B — IN3 / IN420 / 10

Two notes

Motor B's inputs are wired inverted (20 / 10 rather than 10 / 20) so that a positive speed on both channels drives forward without the firmware correcting per side.

All four motor pins are driven LOW at the very start of startup, before anything else, because ESP32 pins float during boot and a floating H-bridge input makes the tracks lurch.

Numbering

The numeric prefix is the only thing tying a mesh to its place in the assembly. Add a part and it takes the next number; nothing is renumbered, and nothing is reused.

Screws and horns come from the bag taped to each servo, so there is no separate fastener list.

Not settled

The face plate has no mesh yet, and the track-link count has never been checked against a built robot. Both are open.

Files and formats

Everything under mechanical/. The CAD is the master and the meshes are derived from it, so a corrected STL is a dead end — the next export overwrites it.

Two things that will waste your afternoon

All of the geometry is tracked through Git LFS. Run git lfs install before cloning, or every file arrives as a short text pointer.

Rhino 8 does not read tessellated STEP. Rhino users should take the .3dm, which is the same geometry.

The two whole-robot models carry the assembly rather than a single printable part: chassis, head, tracks, motors, boards and displays, all in place.

They are the reason a board designer can check that a layout fits before anyone fabricates one. Full notes on how they were reduced from the 930 MB working model are in mechanical/README.md.

Licensing

CoversLicence
Software — firmware, controller app, websiteMIT
Hardware — mechanical design, electronicsCERN-OHL-S-2.0

CERN-OHL-S is strongly reciprocal: build and distribute a modified Marvin and you share your design changes too. The code is permissive; the object is copyleft.

This is the conventional open-hardware split, and it is deliberate. It is also why the CAD master, not just the meshes, lives in the repository.
